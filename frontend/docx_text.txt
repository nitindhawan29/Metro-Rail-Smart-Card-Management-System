Frontend Development Handoff Guide
Stages 10 to 15
Purpose: allow frontend work to proceed in parallel with backend Stages 5–9 without breaking the project or creating merge conflicts.
Frozen starting point: repository after Stage 4
Frontend stack: HTML + CSS + JavaScript
Database/backend files are read-only for the frontend developer.
1. Purpose and Scope of This Handoff
This document is for the team member implementing Stages 10–15 while backend Stages 5–9 are being developed separately. The main objective is to finish a complete, integration-ready frontend without changing the database or backend implementation.
Start from the shared repository exactly at the Stage 4 baseline.
Work only inside the frontend/ directory unless this guide explicitly says otherwise.
Do not modify database schema, backend routes, controllers, .env files, Node packages, or SQL files.
Build the frontend against the API contract in this document, using a mock adapter until Stage 16.
At Stage 16, both developers will integrate the finished frontend with the finished backend together.

3. Git Workflow for Parallel Development
The frontend developer should branch from the Stage 4 commit pushed by the backend developer. This keeps frontend changes separate and makes Stage 16 merging safe because the two developers are primarily changing different folders.
# After cloning/pulling the Stage 4 repository
git checkout <stage-4-shared-branch>
git pull
git checkout -b frontend-stages-10-15
git push -u origin frontend-stages-10-15
Before every commit, verify that only frontend files changed:
git status
git diff --name-only
Expected changed paths should begin with:
frontend/
If backend/ or database/ appears unexpectedly, revert those accidental changes before committing.

5.1 Response Pattern the Frontend Should Expect
For list/read operations, use the following shape as the main contract:
{
  "success": true,
  "data": [ ... ]
}
For successful create/update/delete operations, rely only on success and message, then re-fetch the list. Do not make the UI depend on optional response details such as insertId.
{
  "success": true,
  "message": "Operation completed successfully"
}
For an error:
{
  "success": false,
  "message": "Readable error message"
}

7. Parallel-Development Adapter (Very Important)
Because the frontend developer starts from Stage 4, most CRUD APIs do not exist yet. Do not wait for the backend and do not modify it. Instead, use one controlled mock switch.
// frontend/js/config.js
const APP_CONFIG = {
  API_BASE_URL: 'http://localhost:5000/api',
  USE_MOCK_API: true
};
At Stage 16 integration, the team should change only:
USE_MOCK_API: false
The page files should not care whether data came from mock storage or MySQL. Both adapters must expose the same function names and return the same shape.

7.2 Safe Request Wrapper Pattern
Real backend communication should be centralized. A recommended api.js pattern is:
async function request(path, options = {}) {
  const response = await fetch(`${APP_CONFIG.API_BASE_URL}${path}`, {
    headers: {
      'Content-Type': 'application/json',
      ...(options.headers || {})
    },
    ...options
  });
  const body = await response.json();
  if (!response.ok || body.success === false) {
    throw new Error(body.message || 'Request failed');
  }
  return body;
}
Page files should call wrapper functions such as createPassenger(data), not fetch() directly.

14. Mock Data Rules
Mock mode exists only because backend Stages 5–9 are being developed in parallel. It must imitate the real contract closely so Stage 16 is a configuration/integration task rather than a frontend rewrite.
Use the exact frozen field names; never invent alternative names such as mobile, cardNo, stationName, or fare.
Use realistic IDs and relationships. Every card passenger_id must refer to an existing passenger; every transaction card_id/station_id must refer to existing records.
Generate IDs in mockApi.js only; page scripts should never invent IDs.
Mock create/update/delete functions should return objects shaped like the real API.
If using localStorage for mock persistence, isolate every localStorage call inside mockApi.js. No page file should access localStorage directly.
Clearly mark mock data as DEVELOPMENT ONLY in source comments. It must not be presented as MySQL persistence in the final demo.

17. Stage 16 Integration Preparation — Do This Before Handoff
1.  Make sure USE_MOCK_API is still controlled from one place in config.js.
2.  Search the entire frontend folder for direct fetch( calls. Except api.js, there should be none.
3.  Search for hard-coded localhost:5000 strings. Except config.js/api.js, there should be none.
4.  Search for old field aliases such as mobile, cardNo, stationName, fare. Replace them with frozen contract names.
5.  Verify every dropdown stores IDs as values, not visible names.
6.  Verify dashboard uses existing list service functions only.
7.  Run all mock CRUD flows after a full page refresh.
8.  Commit all work and ensure git status is clean.
9.  Push the frontend branch. Do not merge it into the backend branch yet.
