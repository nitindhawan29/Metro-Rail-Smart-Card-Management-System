# Metro Rail Smart Card Management System

## Stage 9 Backend API Contract

**Status:** Frozen for Stage 16 frontend integration  
**Local API Base URL:** `http://localhost:5000/api`

This document defines the backend routes, request fields, response fields, validation rules, and HTTP status conventions that the frontend must follow. The frontend should use the exact route names and field names in this document.

---

## 1. Common Response Format

### Successful list/read response

```json
{
  "success": true,
  "data": []
}
```

For a single record, `data` is an object instead of an array.

### Successful create response

```json
{
  "success": true,
  "message": "Record added successfully",
  "<generated_id_field>": 1
}
```

### Successful update/delete response

```json
{
  "success": true,
  "message": "Operation completed successfully"
}
```

### Error response

```json
{
  "success": false,
  "message": "Error message"
}
```

---

## 2. HTTP Status Convention

| Status | Meaning |
|---:|---|
| `200` | Successful GET, PUT or DELETE |
| `201` | Record created successfully |
| `400` | Invalid or missing input |
| `404` | Requested resource or referenced record not found |
| `409` | Database conflict, such as duplicate card number or protected delete |
| `500` | Unexpected backend/database error |

# 4. Passenger API

Base route: `/api/passengers`

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/passengers` | Get all passengers |
| GET | `/api/passengers/:id` | Get one passenger by ID |
| POST | `/api/passengers` | Create passenger |
| PUT | `/api/passengers/:id` | Update passenger |
| DELETE | `/api/passengers/:id` | Delete passenger |

## Passenger fields

- `passenger_id` — generated by MySQL
- `passenger_name`
- `country_code`
- `mobile_number`
- `email` — optional

## POST/PUT request body

```json
{
  "passenger_name": "Rahul Sharma",
  "country_code": "+91",
  "mobile_number": "9876543210",
  "email": "rahul@gmail.com"
}
```

## Passenger validation

- `passenger_name`, `country_code`, and `mobile_number` are required.
- `country_code` must match `+` followed by 1 to 4 digits, with the first digit non-zero.
- `mobile_number` must contain 4 to 14 digits.
- Total international number length, excluding `+`, must not exceed 15 digits.
- `email` is optional; when provided it must be a valid email format.

## GET response fields

```text
passenger_id
passenger_name
country_code
mobile_number
email
```

## Important delete behavior

A passenger cannot be deleted while a SmartCard references that passenger. The backend returns `409 Conflict`.

# 5. Smart Card API

Base route: `/api/cards`

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/cards` | Get all smart cards with passenger name |
| GET | `/api/cards/:id` | Get one smart card |
| POST | `/api/cards` | Create smart card |
| PUT | `/api/cards/:id` | Update smart card |
| DELETE | `/api/cards/:id` | Delete smart card |

## POST request body

```json
{
  "passenger_id": 1,
  "card_number": "METRO1001",
  "balance": 500
}
```

`balance` is optional during creation. If omitted, the backend stores `0`.

## PUT request body

```json
{
  "passenger_id": 1,
  "card_number": "METRO1001",
  "balance": 750
}
```

`passenger_id` and `card_number` are required. If `balance` is omitted during update, the existing balance is preserved.

## Smart card validation

- `passenger_id` must be a positive integer and must reference an existing passenger.
- `card_number` must be exactly `METRO` followed by four digits, for example `METRO1001`.
- `card_number` is unique.
- `balance`, when provided, must be a valid non-negative number.

## GET response fields

```text
card_id
passenger_id
passenger_name
card_number
balance
```

`passenger_name` is returned through the Passengers-SmartCards JOIN.

## Important delete behavior

A smart card cannot be deleted while Transactions reference that card. The backend returns `409 Conflict`.

# 6. Station API

Base route: `/api/stations`

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/stations` | Get all stations |
| GET | `/api/stations/:id` | Get one station |
| POST | `/api/stations` | Create station |
| PUT | `/api/stations/:id` | Update station |
| DELETE | `/api/stations/:id` | Delete station |

## POST/PUT request body

```json
{
  "station_name": "MP Nagar",
  "line_name": "Orange Line"
}
```

## Station validation

- `station_name` and `line_name` are required.
- Values containing only spaces are rejected.
- `station_name` cannot exceed 100 characters.
- `line_name` cannot exceed 50 characters.
- Leading and trailing spaces are removed before storage.

## GET response fields

```text
station_id
station_name
line_name
```

## Important delete behavior

A station cannot be deleted while Transactions reference that station. The backend returns `409 Conflict`.

# 7. Transaction API

Base route: `/api/transactions`

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/transactions` | Get all transactions with joined details |
| GET | `/api/transactions/:id` | Get one transaction with joined details |
| POST | `/api/transactions` | Create transaction |
| PUT | `/api/transactions/:id` | Update transaction |
| DELETE | `/api/transactions/:id` | Delete transaction |

## POST/PUT request body

```json
{
  "card_id": 1,
  "station_id": 1,
  "fare_amount": 25
}
```

The frontend must not send `transaction_id` or `transaction_date`. `transaction_id` is auto-generated and `transaction_date` uses the database default timestamp on creation.

## Transaction validation

- `card_id`, `station_id`, and `fare_amount` are required.
- `card_id` and `station_id` must be positive integers.
- The referenced smart card and station must exist.
- `fare_amount` must be a valid non-negative number.

## GET response fields

```text
transaction_id
card_id
card_number
passenger_id
passenger_name
station_id
station_name
line_name
transaction_date
fare_amount
```

These fields are produced using joins between Transactions, SmartCards, Passengers, and Stations.

# 8. Frozen Frontend Integration Rules

1. Use the exact API paths documented here.
2. Use the exact JSON field names documented here.
3. Do not rename backend fields in requests.
4. Do not send generated primary-key fields in create forms.
5. Smart Card forms should display passenger names but submit `passenger_id`.
6. Transaction forms should display card/station labels but submit `card_id` and `station_id`.
7. Display backend `message` values for failed operations where appropriate.
8. Treat HTTP `409` as a user-visible conflict rather than a generic server failure.
9. The frontend should not modify backend routes, database schema, or controller contracts during Stage 10-15.
10. Any required contract change must be handled jointly during Stage 16 integration.
